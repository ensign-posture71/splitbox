## Модель данных

Единственный источник истины — `config.yaml` в томе `state`
(`/var/lib/splitbox/config.yaml` внутри контейнеров). Всё остальное —
конфиг sing-box, конфиги устройств WireGuard, стартовый конфиг
AdGuard — **производное** и пересобирается из него.

```yaml
mode: vps | lan-gateway     # задаётся при установке, не в панели
endpoint_host: …            # внешний адрес коробки для конфигов устройств
admin: {password_hash, session_secret}
own_servers: [ … ]          # «свои» серверы: доверенный выход
subscriptions: [ … ]        # ссылки на подписки + постоянный HWID
manual_nodes: [ … ]         # одиночные vless:// / trojan:// / ss://
policies:
  rulesets: {"vernette:youtube": fast, …}   # готовые наборы
  domains:  [{value, policy}]               # свои домены
  networks: [{value, policy}]               # свои подсети
wireguard: {listen_port, subnet, private_key, peers: [ … ]}
dns: {adblock, upstreams}
```

Формат YAML выбран сознательно: файл читается глазами, diff'ается,
бэкапится копированием и чинится руками, если панель недоступна.
Схема описана Pydantic-моделью (`core/splitbox/model.py`) — некорректное
значение не попадёт в файл.

Запись всегда атомарна: временный файл **в той же директории** →
`os.replace`. Не в `/tmp`: это часто другая файловая система, и
переименование оттуда падает с «Invalid cross-device link».

Поле `schema_version` и функция миграции в `store.py` существуют,
чтобы обновление коробки никогда не требовало ручной правки настроек.

## Сетевая архитектура

Все контейнеры живут в **одном сетевом пространстве**: `gateway` им
владеет, остальные подключаются через `network_mode: service:gateway`.

```
                    ┌─ сетевое пространство gateway ──────────────┐
    51820/udp ─────►│  sing-box: WG-сервер, tproxy, SOCKS-проба   │
    8443/tcp  ─────►│  AdGuard: 127.0.0.1:53                      │
                    │  веб-панель: 0.0.0.0:8443                   │
                    │  clash API: 127.0.0.1:9090                  │
                    └─────────────────────────────────────────────┘
```

Что это даёт:

- общий `127.0.0.1` — правило перехвата `tproxy to 127.0.0.1:7895`
  работает без ухищрений, панель ходит к AdGuard и к API sing-box
  по локальному адресу;
- наружу публикуется ровно то, что нужно, — один раз, на `gateway`;
- процессы при этом изолированы по контейнерам и обновляются независимо.

Разделение обязанностей строгое: **панель не имеет доступа к докеру.**
Чтобы попросить перезапуск sing-box, она пишет команду в unix-сокет
супервизора (`state/run/gateway.sock`). Компрометация панели не даёт
власти над хостом.

## Путь трафика

**Через WireGuard.** Устройство поднимает туннель к коробке. WireGuard
реализован *внутри* sing-box (endpoint в пространстве пользователя), а не
модулем ядра, поэтому трафик пира сразу попадает в правила маршрутизации,
минуя ядро. Побочный выигрыш: в режиме VPS контейнеру не нужны
привилегии и поддержка WireGuard ядром вообще.

**Через локальную сеть** (только режим шлюза). Коробка назначена шлюзом,
транзитные пакеты перехватываются в `prerouting` и заворачиваются в
sing-box через TPROXY:

```
nftables prerouting (priority mangle)
  ├─ приватные сети            → return   ← предохранитель, стоит первым
  └─ tcp/udp: mark 1, tproxy to 127.0.0.1:7895
ip rule fwmark 1 lookup 100
ip route local 0.0.0.0/0 dev lo table 100
```

Правило про приватные сети стоит первым **намеренно**: без него в туннель
уедет и трафик к самой коробке, включая SSH и панель, — то есть
диагностировать поломку будет уже неоткуда.

## Логика маршрутизации

Порядок правил в конфиге sing-box = приоритет. Сверху вниз:

| # | Правило | Куда | Зачем |
|---|---|---|---|
| 1 | `sniff` | — | достать имя сайта из начала соединения |
| 2 | DNS-запросы | перехват | ответить через AdGuard, наружу не пускать |
| 3 | приватные адреса | напрямую | внутрисетевое не уходит в туннель |
| 4 | с пробного входа | свой сервер | проверка здоровья идёт боевым путём |
| 5 | наборы «быстрый» | группа автовыбора | |
| 6 | наборы «свой» | свой сервер | |
| 7 | подсети «быстрый»/«свой» | соответственно | для протоколов без имени сайта |
| 8 | домены «быстрый»/«свой» | соответственно | ваши списки |
| — | всё прочее | **напрямую** | |

Тонкости, каждая из которых оплачена отладкой:

- **Перехват DNS стоит выше правила про приватные адреса.** Клиент
  WireGuard шлёт запросы на адрес коробки внутри туннельной подсети,
  а он приватный: правило ниже отправило бы запрос «напрямую» — на
  адрес, которого в сети хоста не существует.
- **«Быстрый» стоит выше «своего».** Если сервис помечен как быстрый —
  это осознанное решение владельца, оно не должно перебиваться
  умолчанием.
- **Подсети — отдельными правилами, а не полем в правиле доменов.**
  Внутри одного правила sing-box объединяет условия по И, и запись
  «домен + подсеть» потребовала бы совпадения обоих сразу.
- **Точное совпадение и суффикс задаются раздельно.** Голый суффикс
  `example.com` совпал бы и с `notexample.com`; точка впереди делает
  совпадение по границе имени.
- **Умолчание для новых записей — «свой»**, а не «быстрый»: чужие
  серверы из подписки видят весь проходящий трафик, попадание туда
  должно быть выбором, а не случайностью.
- **Последнее правило — «напрямую».** Цена ошибки — лишний крюк, а не
  оборванная связь.

Списки блокировок sing-box скачивает сам раз в сутки и **кэширует на
диск**. Без кэша перезапуск требовал бы доступа к GitHub — то есть его
недоступность означала бы отказ маршрутизации.

## Применение настроек

Любое изменение в панели проходит один и тот же путь:

```
изменить config.yaml (атомарно)
      │
      ▼
собрать новый конфиг sing-box  →  singbox.json.new
      │
      ▼
sing-box check                 →  ошибка? стоп, боевой конфиг не тронут
      │ успех
      ▼
os.replace → singbox.json      →  атомарная подмена
      │
      ▼
команда «reload» в сокет супервизора → перезапуск sing-box
```

Проверка настоящей утилитой `sing-box check`, а не собственной
валидацией: опечатка в списке доменов не должна ронять интернет всему
дому. При неудачной проверке пользователь видит текст ошибки, а
работающая конфигурация остаётся прежней.

Известный компромисс: перезапуск рвёт активные соединения на секунду-две.
WireGuard-сессии восстанавливаются сами.

Деградации вместо отказов:

| Ситуация | Поведение |
|---|---|
| нет подписок | правила «быстрый» указывают на свой сервер |
| нет своего сервера | правила «свой» указывают на группу автовыбора |
| несколько своих серверов | между ними поднимается своя группа автовыбора |
| нет вообще ничего | честная ошибка: маршрутизировать некуда |

## Отказоустойчивость

Супервизор `gateway` (`docker/gateway/gateway.py`) раз в 30 секунд
проверяет туннель — **настоящим запросом наружу** через локальный
SOCKS-вход, для которого есть безусловное правило «идти в туннель».
Проверяется результат, а не признак: процесс sing-box может быть жив
при полностью мёртвом туннеле.

Два провала подряд (одиночный сбой не считается) в режиме шлюза →
снимается **только слой перехвата**. Базовый слой с форвардингом и NAT
остаётся, и локальная сеть продолжает работать напрямую. Туннель
починился — слой возвращается автоматически.

Отдельно проверяется наличие самой сетевой обвязки: если правил нет, они
**восстанавливаются**, а не приводят к аварийному режиму.

Сетевая обвязка и sing-box живут в одном процессе-супервизоре
осознанно. В проекте-предшественнике это были две независимые системные
службы, и их рассинхронизация однажды устроила петлю маршрутизации.
Здесь порядок «сначала сеть, потом sing-box, при остановке снять
правила» зашит в код, и разъехаться они не могут.

## Подписки

Разбор (`core/splitbox/subs.py`) устроен сложнее, чем кажется
необходимым, — и каждая сложность имеет причину:

- **Перебор семи User-Agent.** Панели отдают разное содержимое разным
  клиентам: одному ссылки, другому готовый конфиг, третьему YAML, а
  незнакомому — заглушку. Берётся ответ, в котором живых серверов больше.
- **Постоянный идентификатор устройства (HWID).** Некоторые панели без
  него отдают заглушку. Идентификатор генерируется **один раз при
  добавлении подписки** и хранится: меняющийся занимал бы новый слот
  устройства при каждом обращении и быстро исчерпал бы лимит.
- **Четыре формата разбора** — xray-JSON, sing-box-JSON, clash-YAML и
  голые ссылки (в том числе в base64). Порядок важен: xray-конфиг тоже
  JSON, но со своей структурой.
- **Фильтры.** Отбрасываются адреса-заглушки (их кладут вместо серверов
  при неактивной подписке), профили-ретрансляторы и узлы с голым IP.
  Последнее принципиально: такие узлы обычно расположены внутри страны,
  по задержке выигрывают у зарубежных, и группа автовыбора предпочла бы
  именно их — «заграничный» трафик остался бы дома.

Неизвестные схемы пропускаются молча: подписки часто содержат мусор, и
одна плохая строка не должна лишать пользователя всего резерва. А вот
ссылка, введённая руками, разбирается строго — человек должен увидеть,
что с ней не так.

## Два режима

| | `vps` | `lan-gateway` |
|---|---|---|
| Вход трафика | только WireGuard | WireGuard + вся локальная сеть |
| Сеть контейнера | bridge | host |
| Привилегии | не нужны | `NET_ADMIN`, `NET_RAW` |
| DNS | только внутри туннеля | на адресе машины в сети |
| «Прочий» трафик | выходит с адреса VPS | выходит с местного адреса |
| Fail-open | выключить VPN в приложении | автоматический |

Режим задаётся при установке (`MODE` в `.env`) и синхронизируется в
`config.yaml` при старте — от него зависит, поднимается ли перехват
вообще. Менять его в панели нельзя намеренно: это свойство
развёртывания, а не настройка.

## Разработка и тестирование

```bash
cd core
python3 -m venv .venv && .venv/bin/pip install -e ".[api,dev]"
.venv/bin/python -m pytest
```

Тесты (59) покрывают разбор всех четырёх форматов подписок, фильтры,
модель и хранилище, сборку конфига во всех режимах и деградациях,
ключи WireGuard и все сценарии панели. Эталонные конфиги в
`core/tests/golden/` дополнительно проверяются настоящим
`sing-box check`.

**Режим шлюза нельзя проверить на macOS.** В ядре Docker Desktop
правило `tproxy` считает пакеты, но не доставляет их сокету — это
проверено отдельным прозрачным слушателем, дело не в sing-box. Нужна
виртуальная машина с настоящим ядром Linux и **rootful** докером
(в rootless контейнер не может выполнить `ip rule add` даже с
`NET_ADMIN`):

```bash
limactl start --name=splitbox template://docker
limactl shell splitbox -- sudo sh -c "systemctl unmask docker containerd; systemctl start containerd docker"
docker save splitbox-app splitbox-gateway adguard/adguardhome:v0.107.52 \
  | limactl shell splitbox -- sudo docker load
limactl shell splitbox -- sudo sh -c "cd /путь/к/splitbox && MODE=lan-gateway \
  docker compose -f compose.yaml -f compose.lan.yaml -f compose.dev.yaml up -d --no-build"
```

Проверить путь WireGuard можно без телефона: поднять sing-box на хосте
как клиента, взяв ключи из скачанного конфига устройства.

## Почему сделано именно так

Короткий список решений, которые выглядят странно, пока не знаешь причины:

**DNS к AdGuard идёт по TCP, а не UDP.** В режиме host-network
двухстековый UDP-сокет AdGuard не мог ответить на `127.0.0.1`
(`sendmsg: invalid argument`). По TCP ответ доходит везде, а кэширование
на обеих сторонах делает накладные расходы незаметными.

**Автоопределение интерфейса выключено.** Оно задумано как страховка от
петель, но в нестандартных окружениях роняло все исходящие соединения с
ошибкой «нет маршрута в интернет». Перехват живёт только в `prerouting`
и собственные соединения sing-box не помечает, поэтому петля здесь
невозможна и страховка не нужна.

**Проба здоровья ходит через отдельный локальный вход.** Если проверять
обычным запросом, он попадёт под общие правила и уйдёт «напрямую» —
проверка покажет зелёный свет на полностью мёртвом туннеле. Поэтому для
пробы есть отдельный вход с безусловным правилом «в туннель».

**Формы не передают параллельные списки значений.** Раньше значение и
его политика приходили двумя списками, и стоило одному элементу
потеряться, как все последующие записи получали чужой режим. Теперь
значение и политика склеены в одно поле — рассинхронизация невозможна
по построению.

**IPv6 у клиентов забирается в туннель целиком.** Сервер IPv6 не
маршрутизирует, но если не забрать у клиента v6-маршрут, часть трафика
утечёт мимо туннеля в сетях, где IPv6 есть.

**Приватный ключ устройства хранится в настройках.** Иначе QR-код
нельзя показать повторно — а нетехническому пользователю это нужно
регулярно. Компромисс в пользу удобства; файл настроек имеет права 600.
