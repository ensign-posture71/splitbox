# Журнал решений

Дополняет `architecture.md` (F1–F8 там). Здесь — только то, что решено/обнаружено
в ходе исполнения. Каждая запись: решение, дата, обоснование.

## D1 — §5: Вариант A (2026-08-17)
Роутер стерит по IP-address-list `abroad`, мозг (домены, geosite, автообновление) — на VM.
VM пушит IP-список на роутер.
**Почему:** fail-open важнее доменной точности для домохозяйства (см. §5 architecture.md).
**Следствие:** нужен sync-скрипт `sync/`; отказ VM = abroad не работает, остальное живёт.

## D2 — Линк роутер↔VM: общий LAN-сегмент (2026-08-17)
VM в `192.168.88.0/24` со статическим IP. Отдельный VLAN и WG p2p отклонены.
**Почему:** максимальная простота и диагностируемость; WG p2p — лишний CPU на слабом hAP ac² (F1).
**Открыто:** конкретный IP для VM — вне DHCP-пула роутера (уточнить после baseline).

## D3 — VPS: реюз существующего VLESS+Reality (2026-08-17)
Шаг 2 сводится к сбору клиентских параметров и проверке, а не к развороту.
**Нужны от владельца:** адрес, порт, UUID, public key, shortId, SNI/dest, flow.
**Хранение:** `secrets/`, вне Git.

## D4 — Доступ: SSH с рабочего Mac (2026-08-17)
Чтение (export, диагностика) и применение — по SSH. Пароли не передаются, авторизация по ключу.

## O4 — wg-хаб для роуминга УЖЕ существует (2026-08-17)
`wg0`, listen-port 51820, `10.200.200.1/24`, три peer'а: client1/2/3 → `.2/.3/.4`.
`wg0` состоит в interface-list `LAN`, поэтому клиенты роуминга проходят input-accept
и выходят в интернет через домашний masquerade.
**Следствие:** шаг 1.3 в основном закрыт. Остаётся вопрос §7.12 — что этим клиентам
давать в новой схеме (work/abroad или только «домой»).

## O5 — Плоскость policy-routing НЕ начата (2026-08-17)
Таблица маршрутизации ровно одна — `main`. Нет `table_work`, `table_vps`.
Нет ни одного mangle-правила. Нет ни одного IPv4 address-list.
**Нет туннеля на работу вообще** — `wg-work` не существует, маршрутов на `10.0.0.0/8` нет.
**Следствие:** шаг 1.2 стартует с нуля и блокирован внешними данными от работы (§7.10, §7.11).

## O6 — ⚠️ fasttrack сломает policy routing (2026-08-17)
В `forward` активно `action=fasttrack-connection` для `established,related`.
Fasttrack уводит пакеты мимо conntrack и mangle — помеченные соединения перестанут
попадать в `table_work`/`table_vps` после первого же пакета.
**Решение (принято, не требует обсуждения):** правила классификатора ставятся ДО fasttrack,
а fasttrack получает исключение для маркируемого трафика.
Это обязательное условие работоспособности шага 1.4, а не опция.

## O7 — В LAN уже живёт Proxmox-парк и свой DNS (2026-08-17)
`/ip dns` форвардит на `192.168.88.45` — это VM `alpine-adguard` (AdGuard Home).
DHCP отдаёт клиентам роутер (`192.168.88.1`), роутер форвардит на AdGuard, fallback `1.1.1.1`.
Другие Proxmox-VM в том же LAN (MAC `BC:24:11:*`): `mcp-docker` .32,
`qbittorrent` .47, `prometheus-pve-exporter` .61. Плюс `HermesAI` .40.
**Следствие 1:** D2 (VM в общем LAN) — это уже сложившийся паттерн, не новое решение.
**Следствие 2:** AdGuard — готовая точка контроля DNS, её надо вписать в схему явно (§7.8, §7.9).
**Следствие 3:** ⚠️ статические адреса инфраструктуры (.40, .45) лежат ВНУТРИ DHCP-пула
`192.168.88.10-254` → риск коллизии. Под sing-box-VM брать адрес из `.2-.9` (вне пула).

## O8 — WAN: публичный IP (2026-08-17)
`ether1` = `91.200.224.139/26` по DHCP, шлюз `91.200.224.129`. Адрес публичный (не CGNAT),
поэтому wg0-хаб принимает входящие штатно.
**Риск:** адрес выдаётся по DHCP — при смене отвалятся клиенты роуминга. Проверить у провайдера,
статический ли он де-факто; иначе нужен DDNS (`/ip cloud`).

## O9 — IPv6 фактически не используется, но не выключен (2026-08-17)
Глобальных IPv6-адресов нет, только link-local. `disable-ipv6: no`, `ipv6-fasttrack-active: yes`.
**Риск:** policy routing проектируется под IPv4. Если провайдер включит RA/PD, часть трафика
уйдёт по IPv6 мимо всей классификации — «за рубеж» протечёт напрямую.
**Решение к принятию:** либо явно выключить IPv6, либо продублировать классификатор для v6.

## O10 — ⚠️ Находки безопасности в baseline (2026-08-17)
1. **Telegram bot token открытым текстом** в `/system script global-config-overlay`
   (owner `hermes`), вместе с chat id. Попадает в любой `/export`. Токен даёт полный
   контроль над ботом. → отозвать и перевыпустить.
2. `/ip service www-ssl address=0.0.0.0/0 disabled=no` — web-интерфейс слушает без
   ограничения по источнику. Фактически прикрыт правилом firewall
   «drop all not coming from LAN», но это защита в один слой. → сузить до LAN.
3. `/ip upnp enabled=yes` (external `ether1`) — любое устройство LAN может само
   открыть порт наружу. Вероятно, поставлено ради `qbittorrent` .47. → решение владельца.
4. **Мёртвые правила защиты:** `detect-port-scanners`, `detect-brute`, `drop-brute`,
   `drop-port-scanners` стоят ПОСЛЕ `drop all not coming from LAN` в цепочке `input`,
   поэтому для WAN-трафика недостижимы. Защиты от брутфорса сейчас нет. → переставить.
5. Пользователь `hermes` (group `write`, из `192.168.88.0/24`) и его скрипты имеют
   политику `password,sensitive,romon`. Сторонний агент с правом записи в конфиг роутера.
   → подтвердить, что это осознанно.
