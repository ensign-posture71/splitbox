# Архитектура: домашний policy-routing шлюз (MikroTik + sing-box VM)

**Статус:** проработана, зафиксирована. Готова к исполнению кодовыми агентами.
**Формат исполнения:** RouterOS-конфиг как скрипт в Git; конфиг VM (sing-box) в Git; скрипт синхронизации в Git.
**Роль этого документа:** передать агентам зрелую архитектуру + границы ответственности + обязательные вопросы к владельцу. Агенты НЕ додумывают недостающее — спрашивают.

---

## 1. Цель

Все устройства домохозяйства (включая телефоны непрофильных пользователей — «мамы/бабушки»)
подключаются к одному шлюзу и получают единообразную маршрутизацию **без настройки на самих устройствах**.
В зависимости от назначения трафик уходит одним из трёх путей:

1. **На работу** — по WireGuard (одному или нескольким туннелям).
2. **Напрямую** — из домашней сети в интернет (это поведение по умолчанию: RU и всё, что не помечено).
3. **За рубеж** — через DPI-устойчивый транспорт (VLESS+Reality) на собственный VPS,
   только для явно заданных доменных/IP-списков.

Требования владельца (зафиксированы): максимально просто; готово к диагностике; развиваемо;
доменная маршрутизация работает идеально и локально (не на стороне VPS); списки автообновляемые;
конфигурация — Git-first.

## 3. Итоговая топология

```
   Внешние устройства (роуминг)                Домашние устройства
     телефон / ноут в разъезде                 (в т.ч. «мама/бабушка»)
              │ WG (внутри РФ, F8)                       │ LAN Wi-Fi/Ethernet
              ▼                                          ▼
       ┌──────────────────────────── MikroTik hAP ac² (L3-ядро, Git) ─────────────────┐
       │  Входы:  bridge-LAN 192.168.88.0/24   +   wg-clients (пул для роуминга)       │
       │                                                                               │
       │  КЛАССИФИКАТОР  (firewall/mangle: mark-connection → mark-routing, симметрия)   │
       │     dst ∈ 10.0.0.0/8  или  work-domains  → table_work → wg-work ──────────────┼─▶ РАБОТА
       │     dst ∈ address-list "abroad"          → table_vps  → линк на VM  ──────────┼─▶ VM
       │     всё остальное (RU + дефолт)          → main       → WAN ──────────────────┼─▶ НАПРЯМУЮ
       └───────────────────────────────────────────────────────────────────┬──────────┘
                                                                            │ только abroad-трафик
                                                                            ▼
                                        ┌──────────── VM на Proxmox (sing-box, Git) ────────┐
                                        │  «мозг обхода»: доменная маршрутизация локально   │
                                        │  (geosite/списки, автообновление, логи)           │
                                        │  outbound: VLESS + Reality  ──────────────────────┼─▶ VPS ─▶ интернет за рубежом
                                        └───────────────────────────────────────────────────┘

   Отказ VM ⇒ путь «за рубеж» деградирует БЕЗОПАСНО (fail-open в direct); работа/LAN/direct продолжают работать.
```

## 4. Компоненты и границы ответственности

### 4.1 MikroTik hAP ac² — L3-ядро (стоковый RouterOS)
Отвечает за: приём всех устройств (LAN + WG-хаб клиентов), NAT, классификацию трафика по назначению,
три таблицы маршрутизации, туннель(и) на работу, отдачу abroad-трафика на VM.
**Не** отвечает за: терминацию VLESS/Reality, «умную» доменную логику, тяжёлые geosite-списки.

Ключевые механики (по документации RouterOS 7):
- Policy routing через **mangle-маркировку** (`mark-connection` в prerouting → `mark-routing` на established),
  а не через `/ip route rule` — потому что на роутере есть NAT, и routing-rules ломают симметрию соединений.
- Отдельная `routing table` (fib) на каждое направление: `table_work`, `table_vps`. Дефолт — в `main`.
- Управление направлениями через **address-list**, а не через новые правила: добавить назначение = добавить запись в список.
- Не маркировать локальный трафик роутера (иначе адреса роутера станут недоступны — известная ловушка v7).

### 4.2 VM на Proxmox — «мозг обхода» (sing-box)
Отвечает за: приём abroad-трафика от роутера; доменную маршрутизацию (geosite + пользовательские списки,
автообновление); egress через VLESS+Reality на VPS; логи для диагностики.
**Не** отвечает за: работу/LAN/direct — они его не касаются и не зависят от него.
Пограничный случай: RU-домены, случайно попавшие в abroad-поток, sing-box может вернуть в direct
(domainStrategy / правило rule).

### 4.3 VPS — Reality-эндпоинт за рубежом
Отвечает за: приём Reality-соединения от VM и выход в интернет за рубежом.
Реюз существующего VLESS/Reality-сервера владельца или разворот нового — вопрос к владельцу (см. §7).

## 5. Единственная открытая развилка: как роутер отдаёт трафик на VM

Это главное решение, которое агенты обязаны проговорить с владельцем. Оба варианта рабочие.

### Вариант A — «тонкий IP-список на роутере, мозг на VM» (рекомендуется)
- Источник истины по abroad-доменам — на VM (geosite + кастом, автообновление).
- VM резолвит домены и **пушит IP-address-list на роутер** (скрипт по таймеру через RouterOS API/SSH).
- Роутер стерит по IP: `mangle dst-address-list=abroad → table_vps → VM`.
- Дефолт роутера = direct через WAN. **Отказ VM ⇒ abroad не работает, но direct/work/LAN живут** (fail-open).
- Устойчив к DoH на клиентах: стеринг по IP не зависит от того, как клиент резолвил домен
  (кроме CDN-случаев с плавающими IP).
- Цена: скрипт синхронизации список→роутер (ещё одна движущаяся часть).

### Вариант B — «всё через VM, роутер тупой»
- Роутер отдаёт на VM **весь** не-work/не-local трафик; sing-box делает полный сплит RU-direct / abroad-Reality.
- Идеальная доменная точность (нативный sing-box), синхронизация списков не нужна.
- Но **VM становится жёсткой зависимостью для всего интернета**: отказ VM = нет интернета у домохозяйства
  (кроме work/local). Требуется health-check + автопереключение дефолта на WAN (netwatch/recursive route).
- Весь трафик делает hairpin через VM.

**Рекомендация:** Вариант A. Для домохозяйства «мамы/бабушки» безопасный отказ (fail-open в direct)
важнее идеальной доменной точности, а источник истины по доменам всё равно остаётся на VM.
Финальный выбор — за владельцем.

## 6. Порядок развёртывания (для агентов)

Гейт F3 уже пройден (плоский WG до VPS не работает) — поэтому сразу двухплоскостная схема.

**Шаг 0. Инвентаризация и Git-скелет.**
Экспорт текущего конфига роутера (`/export`), фиксация в Git как baseline. Заготовка репозитория:
`router/` (RouterOS-скрипты), `vm/` (sing-box конфиг + unit), `sync/` (список→роутер), `README`.

**Шаг 1. Плоскость 1 — роутер (полностью автономна, тестируется без VM):**
1.1 Таблицы `table_work`, `table_vps` (fib).
1.2 wg-work (один или несколько) + маршруты на 10.0.0.0/8, work-домены; проверить handshake с роутера.
1.3 wg-clients — WG-хаб для роуминга: пул адресов, DNS для клиентов, firewall.
1.4 Классификатор mangle (mark-connection → mark-routing), address-list `abroad` (пока ручной тестовый).
1.5 Проверка: work-трафик идёт в туннель; abroad-заглушка помечается; всё прочее — direct.

**Шаг 2. VPS — Reality-эндпоинт.**
Реюз/разворот VLESS+Reality сервера, фиксация клиентских параметров для VM.

**Шаг 3. Плоскость 2 — VM (sing-box):**
3.1 VM на Proxmox: ресурсы, сеть (bridge/VLAN), статический IP, линк роутер↔VM.
3.2 sing-box: inbound для приёма abroad-трафика от роутера (tproxy/redirect), outbound VLESS+Reality на VPS,
    доменная маршрутизация (geosite + кастом), автообновление списков, логи.
3.3 По выбранному варианту (§5): либо sync-скрипт список→роутер (A), либо дефолт-на-VM + failover (B).

**Шаг 4. Отказоустойчивость и диагностика.**
Поведение при отказе VM (fail-open direct). Health-check. Проверочный чек-лист по каждому пути.

## 8. Принципы диагностируемости (заложены в дизайн)

- Каждое направление — отдельная таблица + отдельный интерфейс + отдельный address-list с говорящим именем.
  `/ip route print where routing-table=table_work`, `/interface wireguard peers print`, счётчики на mangle-правилах — всё видно поштучно.
- Управление списками, а не правилами: новый маршрут = запись в address-list.
- sing-box на VM — реальные логи, снапшоты Proxmox, конфиг в Git.
- Безопасный отказ: падение VM не роняет домашний интернет (Вариант A).
